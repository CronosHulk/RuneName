# Правила розробки RuneName

## Архітектура

Дотримуватися гексагональної архітектури (ports and adapters), SOLID та Clean Code.

- Доменне ядро містить правила рун, нормалізацію, дедуплікацію й геометрію. Воно не залежить від FastAPI, SQLAlchemy, AWS, Telegram, HTTP-клієнтів чи файлового сховища.
- Прикладні сценарії координують домен через порти. Інтерфейси портів визначають потреби сценаріїв; адаптери реалізують їх для PostgreSQL, черги, сховища артефактів і провайдера LLM.
- Веб/API та Telegram — вхідні адаптери до спільних сценаріїв. Не дублювати бізнес-логіку між ними.
- Залежності спрямовані всередину: адаптери → прикладний шар → домен. Конкретні адаптери підключаються у composition root.
- ORM-моделі залишаються в адаптері PostgreSQL; вони не є доменними сутностями або контрактами API. Транзакції мають відповідати межам прикладного сценарію.
- AWS і VPS використовують спільні доменні правила, сценарії та PostgreSQL-моделі/міграції. Відмінності середовищ локалізувати в конфігурації та інфраструктурних адаптерах.

## Якість коду

- SOLID: чітка відповідальність модулів, сумісні реалізації портів, невеликі інтерфейси та інверсія залежностей на інфраструктурних межах.
- Зрозумілі назви, явні типи на контрактах, невеликі зв’язні функції, мінімум прихованих побічних ефектів.
- Не створювати інтерфейс для кожної функції або абстракції без реальної межі. Архітектура має відповідати розміру задачі.
- Перевіряти зовнішні дані на вході; визначати помилки домену/сценаріїв незалежно від HTTP-статусів і текстів SDK.
- Домен тестувати без БД та мережі; сценарії — з тестовими адаптерами; SQL, черги й зовнішні інтеграції — окремими інтеграційними перевірками за потреби.
- Під час рев’ю перевіряти напрямок залежностей, відсутність дублювання правил та витікання ORM/SDK у домен.

Скрипти підготовки даних можуть бути самостійними утилітами; не будувати для них штучно всі шари застосунку. Вони мають зберігати походження даних і мати перевірку результатів.
